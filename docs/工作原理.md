# 工作原理

本文说明 ClrScreen 如何识别并跳过开屏广告，以及每个设计取舍背后的原因。

---

## 整体流程

```
系统事件
   │
   ├─ TYPE_WINDOW_STATE_CHANGED（窗口切换：新 Activity / 对话框出现）
   │     │
   │     ├─ 记录 lastWindowChangeAt = now
   │     └─ 排程 6 次定时扫描：0 / 300 / 700 / 1200 / 1800 / 2600 ms
   │
   └─ TYPE_WINDOW_CONTENT_CHANGED（界面内容变化：按钮渲染、倒计时刷新）
         │
         ├─ 超过窗口切换后 6 秒？ ──▶ 忽略
         ├─ 距上次内容扫描不足 250 ms？ ──▶ 忽略（节流）
         └─ 扫描一次
                 │
                 ▼
        ┌──────────────────────┐
        │  取当前活动窗口根节点  │
        │  包名不符则放弃        │
        └──────────┬───────────┘
                   ▼
        ┌──────────────────────┐
        │  广度优先遍历节点树    │
        │  匹配「跳过」信号      │
        └──────────┬───────────┘
                   ▼
        ┌──────────────────────┐
        │  三级点击策略          │
        │  1. 节点 performAction │
        │  2. 可点击祖先         │
        │  3. 手势点击坐标       │
        └──────────┬───────────┘
                   ▼
              成功 ──▶ 计数 +1、进入 1.5 秒冷却、取消剩余排程
```

对应代码：`SkipAdAccessibilityService.kt` 中的 `onAccessibilityEvent`、`scheduleScans`、`tryScanAndClick`。

## 识别：评分制

早期版本用的是「命中任一关键词就点」，误伤严重。现在改为**评分制**：每个信号折算成分值，总分达到阈值 50 才点击。

判定逻辑抽在 [SkipRuleEngine.kt](../app/src/main/java/com/clrscreen/skipad/SkipRuleEngine.kt) 里，不依赖 Android 框架，纯函数，便于推演。

### 信号与分值

| 信号 | 分值 | 说明 |
|------|------|------|
| 文案完全匹配（`跳过` / `Skip Ad` / `关闭广告` 等） | +45 | 最强文案信号 |
| 文案包含关键词（`跳过` / `跳過` / `skip`） | +30 | 弱文案信号 |
| 无障碍描述同上 | +45 / +30 | 与文案同规则，可叠加 |
| 控件 ID 含 `skip` | +40 | 开发者命名习惯，极可靠 |
| 控件 ID 含 `close` 且含 `ad` | +30 | 覆盖「关闭广告」类命名 |
| 位于右下角（右侧 55% 且下部 40%） | +15 | 开屏广告跳过按钮的典型位置 |
| 位于右上角（右侧 55% 且上部 40%） | +12 | 另一种常见位置 |
| 控件面积占屏幕 0~8% | +10 | 按钮通常是小块区域 |
| 控件面积 ≥ 40% | −20 | 几乎全屏，多半是广告本体而非按钮 |
| 自身可点击 | +10 | |
| 有可点击祖先（4 层内） | +5 | |
| 按钮类控件（Button / ImageButton / CompoundButton） | +8 | |

**举例**：一个 `text="跳过 5"`、右下角、面积 1%、自身可点击的 `Button`：

```
文案 +30（含关键词） + ID +0 + 右下角 +15 + 面积小 +10 + 可点击 +10 + 按钮类 +8 = 73 ≥ 50 → 点击
```

一个普通引导页里的 `text="跳过此步骤"`、屏幕中下方、面积 3%：

```
命中排除词 → 直接否决（-1000）
```

### 排除词：一票否决

命中下列任一词组，**无论得分多高都不点**：

```kotlin
private val EXCLUDE_PHRASES = listOf(
    "跳过此步骤", "跳过本步骤", "跳过教程", "跳过引导", "跳过设置",
    "跳过验证", "跳过登录", "跳过片头", "跳过片尾", "跳过介绍", "跳过说明",
)
```

这些词都含「跳过」，但语义是「跳过某个正常流程」，点了会破坏用户体验。这是相比旧版最重要的改进——旧版会把它们全部点掉。

### 前置否决

以下情况直接判负，不参与打分：

| 条件 | 原因 |
|------|------|
| 节点 `enabled=false` | 禁用状态点了无效，且常是倒计时未结束 |
| 节点 `isVisibleToUser=false` | 不可见 |
| 宽或高为 0 | 无有效点击区域 |
| 文案超过 12 字 | 几乎不可能是按钮 |

### 文字长度上限

`MAX_TEXT_LENGTH = 12`。超过 12 字的文案**不参与文案打分**（但若 ID 或描述命中，仍可能靠其它信号达标）。

原因：广告页上的说明性文字常含「跳过」，例如「点击跳过可直接进入应用首页」。这类长句一旦被当成按钮点击，后果比漏点更糟。

实测：13 字的「跳过广告了解更多活动详情吧」不会被点击——这是**设计如此**。

### 为什么用 contains 而非精确匹配

精确匹配会漏掉「跳过 3」「5s | 跳过」「Skip 5s」等带前后缀的形态。用 `contains` 覆盖这些变体，代价是「跳过去」这类词也会得分——但配合排除词和 50 分阈值，已不会误点。

### 多窗口扫描

旧版只看 `rootInActiveWindow`，会漏掉以独立窗口形式存在的广告层。现在会遍历 `getWindows()` 收集所有窗口的根节点：

```kotlin
val roots = ArrayList<AccessibilityNodeInfo>()
rootInActiveWindow?.let { roots.add(it) }
runCatching {
    windows?.forEach { w -> w.root?.let { r -> if (roots.none { it == r }) roots.add(r) } }
}
```

每个窗口只扫描包名与当前前台应用一致的，避免在切换过程中误点别的界面。

### 候选选择

不是「找到第一个就点」，而是遍历完整棵树，选出**得分最高**的候选：

```kotlin
if (verdict is Verdict.Hit) {
    if (best == null || verdict.score > best.verdict.score) {
        best = Candidate(node, verdict)
    }
    if (verdict.score >= 90) return best   // 高分已足够可靠，提前结束
}
```

这样当屏幕上同时存在广告本体的可点区域和角落的跳过按钮时，会选中得分更高的那个。

### 调试日志

Debug 构建会输出每次点击的得分明细：

```bash
adb logcat -s ClrScreen:D
```

```
已点击 pkg=com.example score=105 [无障碍描述「跳过 5」+30, 控件ID含 skip +40,
  位于右下角 +15, 控件面积小(1%) +10, 自身可点击 +10]
```

排查「为什么没点」时，把 `CLICK_THRESHOLD` 临时调低到 0，所有候选的得分都会打出来。

## 点击：三级策略

`clickNode()` 从命中节点开始，逐级尝试更强硬的手段：

```kotlin
// 第 1、2 级：自身或祖先的 ACTION_CLICK
var current: AccessibilityNodeInfo? = node
while (current != null) {
    if (current.isClickable &&
        current.performAction(AccessibilityNodeInfo.ACTION_CLICK)
    ) return true
    current = current.parent
}

// 第 3 级：手势点击节点中心坐标
val bounds = Rect()
node.getBoundsInScreen(bounds)
if (bounds.isEmpty) return false
return dispatchTap(bounds.exactCenterX(), bounds.exactCenterY())
```

| 级别 | 手段 | 适用场景 |
|------|------|---------|
| 1 | 节点自身 `ACTION_CLICK` | 标准 `Button` / `TextView` 带 `setOnClickListener` |
| 2 | 向上找可点击祖先 | 文字在子 `TextView` 上，点击事件挂在父容器 |
| 3 | 手势点击坐标中心 | WebView、自绘控件、`setOnTouchListener` 实现 |

第 3 级用 50 ms 的短按手势：

```kotlin
val path = Path().apply {
    moveTo(x, y)
    lineTo(x + 1f, y + 1f)      // 加 1px 位移，避免零长度路径被系统拒绝
}
val gesture = GestureDescription.Builder()
    .addStroke(GestureDescription.StrokeDescription(path, 0, 50))
    .build()
return dispatchGesture(gesture, null, null)
```

> 手势能力依赖 `android:canPerformGestures="true"`，已在服务配置中开启。

### 优先返回可点击节点

遍历时不直接返回第一个匹配节点，而是：

```kotlin
if (matchesSkip(node)) {
    if (node.isClickable) return node       // 优先：自身可点
    if (fallback == null) fallback = node   // 备选：先记下第一个匹配
}
```

这样「跳过」文字节点和它的可点击父容器同时存在时，会优先选可点击的那个，少走一级回溯。

## 防误触：四道闸门

自动点击最怕误伤正常界面。代码里有四层限制：

### 1. 只监听窗口切换后的 6 秒

```kotlin
if (now - lastWindowChangeAt > SPLASH_WATCH_WINDOW_MS) return   // 6000 ms
```

#### 为什么只监听 6 秒

开屏广告只在 App 启动瞬间出现，通常 3~5 秒。而正常页面里的「跳过此步骤」「跳过教程」是长期存在的。把监听窗口压到 6 秒，就能让绝大部分正常页面的这类文案落在窗口之外。

代价：**6 秒后才出现的跳过按钮不会被点击**（实测延迟 7 秒的按钮未命中）。

### 2. 跳过系统包

```kotlin
private val SYSTEM_PACKAGES = setOf(
    "com.android.systemui",
    "com.android.settings",
    "com.android.provision",
    "com.android.packageinstaller",
    "com.google.android.settings",
    "com.google.android.setupwizard",
    "com.google.android.packageinstaller",
)
```

这些包里的「跳过」属于系统流程——开机向导的「跳过」、权限弹窗的「跳过」、安装器的「跳过」。点了会打断系统配置，必须排除。

同时也排除本应用自身（`pkg == packageName`）。

### 3. 点击后 1.2 秒冷却

```kotlin
private const val CLICK_COOLDOWN_MS = 1200L
...
if (now - lastClickAt < CLICK_COOLDOWN_MS) return
```

防止同一界面被反复点击（例如点击后页面没反应，事件继续触发扫描）。副作用：1.2 秒内连续出现两个广告页时，第二个不会被处理。

### 4. 内容事件节流 200 ms

```kotlin
private const val CONTENT_EVENT_THROTTLE_MS = 200L
```

`TYPE_WINDOW_CONTENT_CHANGED` 在倒计时数字每秒刷新时会密集触发，某些 App 一帧触发多次。不节流会造成大量无效遍历，白耗电。

## 扫描时机：为什么是 11 个时间点

```kotlin
private val SCAN_DELAYS_MS = longArrayOf(0, 250, 600, 1000, 1500, 2100, 2800, 3600, 4500, 5600, 6500)
```

开屏广告的「跳过」按钮不是随 Activity 一起出现的，而是等广告素材加载完、渲染完成才出现，延迟从几百毫秒到几秒不等。WebView 广告尤其慢——要等网页加载、布局、渲染完成。

只扫一次必然漏。11 个时间点覆盖 0~6.5 秒，之后到 8 秒之间靠内容变化事件继续扫描，形成密集覆盖：

```
0   250  600 1000 1500 2100 2800 3600 4500 5600 6500ms          8000ms
│    │    │    │    │    │    │    │    │    │    │               │
●────●────●────●────●────●────●────●────●────●────●···············│
 定时扫描（11 次）                  内容变化事件持续扫描（≤200ms 节流）
```

对比旧版的 6 个时间点（0~2.6 秒），现在能覆盖延迟 3 秒、甚至 6 秒才渲染的慢速广告——实测 `delayed_3s` 从失败变为命中。

关于 8 秒这个边界：`SPLASH_WATCH_WINDOW_MS = 8000L` 控制的是**内容变化事件**的响应窗口，而 `SCAN_DELAYS_MS` 的最后一次定时扫描在 6.5 秒。两者不一致导致 6.5~8 秒之间只剩内容事件这一条路径，若该时段界面恰好没有内容变化，就扫不到。实测 `late_8s`（8 秒才创建按钮）有时命中有时不中，正是这个原因。需要稳定覆盖更慢的广告，两个常量都要调大。

每次定时扫描都会先校验包名，防止在窗口切换过程中误扫到别的 App：

```kotlin
val root = rootInActiveWindow ?: return@Runnable
if (root.packageName?.toString() == pkg) tryScanAndClick(pkg)
```

新窗口出现时先取消上一轮未执行的扫描，避免多轮叠加。

## 服务能力声明

`res/xml/accessibility_service_config.xml`：

```xml
android:accessibilityEventTypes="typeWindowStateChanged|typeWindowContentChanged"
android:accessibilityFeedbackType="feedbackGeneric"
android:accessibilityFlags="flagDefault|flagReportViewIds|flagRetrieveInteractiveWindows"
android:canRetrieveWindowContent="true"
android:canPerformGestures="true"
android:notificationTimeout="100"
```

| 配置 | 作用 |
|------|------|
| `typeWindowStateChanged` | 窗口切换——触发一轮扫描的起点 |
| `typeWindowContentChanged` | 内容变化——捕获异步渲染的按钮 |
| `flagReportViewIds` | 让节点带上 `viewIdResourceName`，ID 信号的前提 |
| `flagRetrieveInteractiveWindows` | 声明可获取交互窗口列表，多窗口扫描的前提 |
| `canRetrieveWindowContent` | 读取节点树，核心能力 |
| `canPerformGestures` | 派发手势，WebView 点击与自绘控件兜底的前提 |
| `notificationTimeout=100` | 事件合并间隔，降低回调频率 |

**只订阅这两类事件**，不监听滚动、文字变化、焦点变化等，从源头减少开销。

## 主界面的状态检测

`MainActivity.isServiceEnabled()` 通过 `AccessibilityManager` 查询当前启用的服务列表：

```kotlin
val enabled = manager.getEnabledAccessibilityServiceList(
    AccessibilityServiceInfo.FEEDBACK_ALL_MASK
)
return enabled.any { it.resolveInfo?.serviceInfo?.packageName == packageName }
```

按包名比对而不是按类名，兼容性更好。`onResume` 时刷新，所以从系统设置返回后状态会立即更新。

跳过计数通过 `companion object` 的静态字段跨组件共享：

```kotlin
@Volatile var skipCount: Int = 0
    private set
```

**注意**：这是内存值，进程被系统回收后归零。v1.1 已把界面文案改为「本次运行以来」以符合实际行为。要改成真正的持久统计，需要落盘（见 [开发指南 · 想让计数持久化](开发指南.md#想让计数持久化)）。

## 保活机制

跳过功能本身不需要保活——无障碍服务由系统托管，重启后自动重新绑定。保活针对的是**进程**，让它别被 LMK 优先回收。

| 组件 | 作用 |
|------|------|
| `KeepAliveService` | 前台服务 + 最低优先级常驻通知，把进程提升到前台级别 |
| `KeepAliveHelper` | 申请电池优化白名单；跳转各厂商自启动管理页 |
| `BootReceiver` | 开机 / 应用更新后恢复前台服务 |
| `Prefs` | 保存「后台守护」开关（唯一持久化数据） |

完整说明见 [保活指南](保活指南.md)。

## 边界情况与已知限制

| 情况 | 行为 | 原因 |
|------|------|------|
| 自绘 Canvas / 图片按钮 | 无法识别 | 无障碍树中没有文字、ID、描述 |
| 按钮 8 秒后才出现 | 不点击 | 超出观察窗口 |
| 文案超过 12 字 | 不参与文案打分 | 长度上限保护 |
| 正常页面的「跳过此步骤」 | **不点击** | 排除词一票否决 |
| 广告页在 1.2 秒内连续出现两次 | 第二次不处理 | 点击冷却 |
| 广告无跳过按钮（只能等倒计时） | 不处理 | 无匹配目标 |
| 进程被系统强杀 | 停止工作 | 需重新开启，见 [保活指南](保活指南.md) |
| 系统包内的「跳过」 | 不处理 | 系统包黑名单 |

### 关于误伤：旧版的问题已解决

v1.0 的误伤很严重——只要是含「跳过」的可点击文案就会点，实测一个静态展示「跳过此步骤」的页面在 9 秒内被点了 4 次。

v1.1 引入排除词后，这类文案在打分前就被否决：

```kotlin
for (phrase in EXCLUDE_PHRASES) {
    if (text.contains(phrase) || desc.contains(phrase)) {
        return Verdict.Miss(-1000, listOf("命中排除词「$phrase」"))
    }
}
```

实测结果：「跳过此步骤」「跳过教程」「跳过片头」全部不再被点，且**没有牺牲任何正向场景的命中率**（19 项判定全部通过）。

### 弹窗同样会触发窗口切换

一个常见误解：以为「引导页是弹窗，不是新窗口，所以不会被扫描到」。

**这是错的。** `TYPE_WINDOW_STATE_CHANGED` 对对话框同样会触发（代码注释写的就是「新窗口（Activity 或对话框）」）。真正的保护来自排除词和评分阈值，不是窗口类型。

### WebView 的点击陷阱

这是一个实测中发现的隐蔽问题，值得单独说明。

无障碍的 `performAction(ACTION_CLICK)` 在 WebView 内的节点上会**返回 true 但什么都不做**：

```
D ClrScreen: 已点击 pkg=com.example.demo score=105 [...]   ← 以为成功了
（网页毫无反应）
```

后果是双重的：广告没跳过，计数还虚增了。

而同样坐标的手势点击可以正常触发网页的链接跳转。所以现在对 WebView 内的节点**优先用手势**：

```kotlin
private fun clickNode(node: AccessibilityNodeInfo): Boolean {
    if (isInsideWebView(node)) {
        if (tapCenter(node)) return true          // WebView 优先手势
        return performClickUpwards(node)
    }
    if (performClickUpwards(node)) return true
    return tapCenter(node)
}
```

`isInsideWebView()` 沿祖先链最多查 8 层，看是否出现 `android.webkit.WebView`。

## 性能开销

| 项目 | 数值 |
|------|------|
| 单次遍历 | 一次 BFS，通常几十到几百个节点，耗时毫秒级 |
| 触发频率 | 窗口切换后 11 次定时 + 内容变化（≤5 次/秒） |
| 空闲时 | 零开销——事件不触发就完全不执行 |
| 内存 | 无缓存、无队列堆积，节点用完即弃 |
| 网络 | 无 |

服务只在收到事件时工作，不轮询、不常驻定时器。

唯一常驻的是前台服务（保活用），它不做事，只挂一条通知。
