# 后台保活指南

Android 的后台管理越来越激进，国产 ROM 尤其如此。本文说明 ClrScreen 做了哪些保活措施、效果如何、以及还需要你手动做什么。

---

## 先说清楚一件事

**无障碍服务本身不需要保活。**

这是一个常见误解。系统会记住「用户启用了哪个无障碍服务」，重启手机后自动重新绑定，不需要任何 App 参与。

实测（Android 17 模拟器，冷重启）：

```
重启前:  enabled_accessibility_services = com.clrscreen.skipad/...
        accessibility_enabled = 1
        Bound services = {...}

重启后:  enabled_accessibility_services = com.clrscreen.skipad/...   ← 保持
        accessibility_enabled = 1                                    ← 保持
        Bound services = {...}                                       ← 自动重新绑定
```

**所以「开机自启」要保的不是无障碍服务，而是 App 进程本身**——进程活着，前台服务才能常驻，才能降低后续被 LMK 回收的概率。

---

## ClrScreen 做了什么

### 0. 先说实测结论：进程优先级由什么决定

在 Android 17（API 37）模拟器上逐项测量 `oom_score_adj`（值越小越不易被 LMK 回收）：

| 配置 | `oom_score_adj` | `procState` | 含义 |
|------|----------------|-------------|------|
| 普通后台（无前台服务、无无障碍） | **700** | cached | 随时可能被回收 |
| 仅前台服务（无障碍关闭） | **50** | FGS | 优先级最高档 |
| 仅无障碍绑定（前台服务关闭） | **100** | FGS(5) | 与前台服务同级 |
| 前台服务 + 无障碍（默认） | **100** | FGS(5) | 同上 |

**两个重要发现：**

1. **无障碍绑定本身就会把进程提升到前台服务级别（adj=100）。** 这是很多人不知道的——只要用户开启了无障碍服务，进程就不会被当成普通后台应用对待。

2. **前台服务单独存在时 adj=50，叠加无障碍后反而变成 100。** 这是 Android 的 adj 计算取「最合适档位」的结果，不是 bug。意味着**对本应用而言，前台服务并不带来额外的优先级收益**。

那为什么还保留前台服务？见下节。

### 1. 前台服务 + 常驻通知

`KeepAliveService` 用最低优先级通知把进程提升到前台级别。

```kotlin
startForeground(NOTIFICATION_ID, buildNotification())
```

通知渠道设为 `IMPORTANCE_MIN`：不响铃、不弹窗、不显示角标，只在通知栏占一行。

**实际收益**（不是优先级，而是这三点）：

- **无障碍被用户关闭时兜底**：此时 adj 从 700 提升到 50，进程仍能存活
- **进程有可见的存在感**：用户能知道它在工作，也方便一键回到 App
- **配合电池白名单**，让系统在 Doze 时不做激进回收

**局限**：无法对抗用户的「强行停止」，也无法对抗厂商 ROM 的「一键清理」。

> 如果你只在意「开着无障碍时的存活能力」，可以关掉常驻通知——实测优先级不变（都是 100）。但一旦无障碍被系统或用户关闭，没有前台服务就只剩 adj=700 的普通后台待遇。

### 2. 电池优化白名单

申请 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`，让系统在 Doze 模式下不冻结本应用。

主界面会显示当前状态：

- ✔ 已加入电池优化白名单
- ✖ 未加入白名单，后台可能被系统冻结

点击「申请忽略电池优化」会弹出系统确认框。

### 3. 开机自恢复

`BootReceiver` 监听 `BOOT_COMPLETED` / `LOCKED_BOOT_COMPLETED` / `MY_PACKAGE_REPLACED`，在开机或应用更新后重新拉起前台服务。

```kotlin
when (intent.action) {
    Intent.ACTION_BOOT_COMPLETED,
    Intent.ACTION_LOCKED_BOOT_COMPLETED,
    Intent.ACTION_MY_PACKAGE_REPLACED -> {
        if (Prefs.isKeepAliveEnabled(context)) {
            KeepAliveService.start(context)
        }
    }
}
```

只有用户开启过「常驻通知」开关才会恢复，不强推。

**实测**：重启后未打开 App，进程 PID 已存在（1850），前台服务已运行，无障碍服务仍为启用状态。

### 4. 厂商自启动引导

Android 没有统一的自启动管理 API，各家 ROM 的入口都是私有 Activity。`KeepAliveHelper.openAutoStartSettings()` 按厂商逐个尝试跳转：

| 厂商 | 尝试的组件 |
|------|-----------|
| 小米 / Redmi | `com.miui.securitycenter/...AutoStartManagementActivity`<br>`com.miui.powerkeeper/...HiddenAppsConfigActivity` |
| 华为 / 荣耀 | `com.huawei.systemmanager/...StartupNormalAppListActivity`<br>`com.huawei.systemmanager/...ProtectActivity` |
| OPPO / realme / 一加 | `com.coloros.safecenter/...StartupAppListActivity`<br>`com.oplus.safecenter/...StartupAppListActivity` |
| vivo / iQOO | `com.vivo.permissionmanager/...BgStartUpManagerActivity` |
| 三星 | `com.samsung.android.lool/...BatteryActivity` |

全部失败时回退到「应用详情页」，由用户手动找。

**这一项无法自动化。** 系统不允许应用给自己加自启动白名单，必须用户手动确认。

## 你需要手动做什么

### 必做（一次性）

1. **开启无障碍服务** —— 这是功能前提，见 [使用指南](使用指南.md#二开启服务必做)
2. **申请电池优化白名单** —— 主界面点「申请忽略电池优化」，在系统弹窗点「允许」

### 强烈建议

3. **允许自启动** —— 主界面点「前往自启动设置」，在系统页面里允许 ClrScreen 自启动

### 按厂商的额外设置

| 系统 | 设置位置 |
|------|---------|
| 小米 / Redmi | 设置 → 应用设置 → 应用管理 → ClrScreen → 省电策略 → **无限制**<br>最近任务卡片下拉 → **锁定** |
| 华为 / 荣耀 | 设置 → 电池 → 应用启动管理 → ClrScreen → 关闭「自动管理」，三项全部允许 |
| OPPO / 一加 / realme | 设置 → 电池 → 应用耗电管理 → ClrScreen → 允许**后台运行**、允许**自启动** |
| vivo / iQOO | 设置 → 电池 → 后台高耗电 → 允许 ClrScreen<br>设置 → 应用管理 → 权限管理 → 自启动 → 允许 |
| 三星 | 设置 → 电池 → 后台使用限制 → 从「休眠应用」中移除 ClrScreen |

### 检查这两项

- **开发者选项 → 不保留活动**：如果开启，每次离开界面都会销毁 Activity，服务会频繁重启。**请关闭**。
- **省电模式 / 超级省电**：部分 ROM 在省电模式下会强制冻结后台，即使加了白名单。

## 效果边界

诚实说明各措施的覆盖范围，以及实测验证过的强度：

| 措施 | 能防住 | 防不住 |
|------|--------|--------|
| 无障碍绑定 | `am kill`、`background_process_limit=0`、内存 trim 各级别 | 用户手动关闭开关、`force-stop` |
| 前台服务 | 无障碍被关时把 adj 从 700 提到 50 | 用户「强行停止」、厂商「一键清理」 |
| 电池优化白名单 | Doze 冻结、后台限制 | 厂商自带的省电策略（需单独设置） |
| 开机自恢复 | 重启后进程消失 | 用户禁用自启动权限 |

**实测强度**（Android 17 模拟器）：

| 攻击手段 | 结果 |
|---------|------|
| `am kill`（模拟 LMK 回收） | ✅ 存活 |
| `am send-trim-memory` 四级（LOW/CRITICAL/MODERATE/COMPLETE） | ✅ 全部存活 |
| `background_process_limit=0` | ✅ 存活 |
| `am force-stop`（用户强行停止） | ❌ 被杀，且无障碍设置被清空 |
| 冷重启 | ✅ 进程自动恢复，无障碍设置保留 |

**没有任何方案能保证 100% 不被杀。** 国产 ROM 的清理策略是系统级的，应用层无法对抗。

唯一确定杀得掉的是 `force-stop`——这是用户主动行为（设置里「强行停止」或厂商「一键清理」），任何应用都无法抵抗。

## 验证保活是否生效

### 检查进程优先级（最直接）

```bash
PID=$(adb shell pidof com.clrscreen.skipad)
adb shell cat /proc/$PID/oom_score_adj
```

对照上文的表判断：

| 输出值 | 含义 |
|--------|------|
| `100` | 正常状态（无障碍已开，前台服务级别） |
| `50` | 前台服务在跑但无障碍被关了 |
| `700` | ⚠️ 普通后台，随时可能被回收 |

### 检查前台服务

```bash
adb shell dumpsys activity services com.clrscreen.skipad | grep -A2 KeepAliveService
```

应看到 `isForeground=true`：

```
* ServiceRecord{... com.clrscreen.skipad/.KeepAliveService}
  isForeground=true foregroundId=1001 ...
```

### 检查电池白名单

```bash
adb shell dumpsys deviceidle whitelist | grep clrscreen
```

应输出 `user,com.clrscreen.skipad,<uid>`。

### 检查开机自恢复

```bash
# 重启前记下 PID
adb shell pidof com.clrscreen.skipad

adb reboot
# 等启动完成后再查，未打开 App 也应看到 PID
adb shell pidof com.clrscreen.skipad
```

### 检查通知是否可见

```bash
adb shell dumpsys notification --noredact | grep "com.clrscreen.skipad"
```

应看到 `id=1001` 且带 `FOREGROUND_SERVICE` 标志。

### 主动测试能否被杀

```bash
# 模拟系统低内存回收：有前台服务/无障碍绑定时应当杀不掉
adb shell am kill com.clrscreen.skipad
adb shell pidof com.clrscreen.skipad   # 应仍返回 PID
```

实测：**完整配置下 `am kill` 无法杀掉进程**，`background_process_limit=0`（系统最多保留 0 个后台进程）时也存活。

## 内存占用实测

在 Android 17 模拟器（4GB 内存）上测得：

| 状态 | PSS | 说明 |
|------|-----|------|
| 冷启动后 | 24.8 MB | 含 UI 初始化 |
| 后台空闲 3s | 25.8 MB | |
| 后台空闲 60s | 25.5 MB | 无增长 |
| 扫描广告时（10 个场景） | 24.6 ~ 26.3 MB | 波动在噪声范围内 |
| 30 轮扫描压力测试后 | 25.9 MB | 相比首轮仅 +63 KB |

**结论：无内存泄漏。** 30 轮连续扫描（约 5 分钟）后内存增长 63 KB，属于测量噪声。

CPU 方面：空闲时 `%CPU = 0.0`，扫描时开销主要在目标应用侧（遍历节点树是毫秒级操作）。

内存构成（冷启动，单位 KB）：

```
Java Heap:      1,436        Code:        1,768
Native Heap:   11,740        Stack:         416
Private Other:  4,624        System:      4,804
TOTAL PSS:     24,788
```

Native Heap 占大头（11.7 MB），来自 Kotlin 运行时与系统图形库，属于正常水平。

## 如果还是被杀

按顺序排查：

1. **主界面两个状态是否都是 ✔？** 无障碍服务、电池白名单
2. **自启动是否允许？** 去系统设置确认
3. **是否开了省电模式？** 关掉试试
4. **是否开了「不保留活动」？** 开发者选项里关掉
5. **厂商是否有一键清理？** 把 ClrScreen 加入清理白名单，或锁定最近任务卡片
6. **通知是否被隐藏？** 如果系统隐藏了常驻通知，前台服务可能被降级

实在不行，把 ClrScreen 加到桌面方便的位置，发现失效时手动打开一次即可——打开 App 会自动重启前台服务。

---

## 关掉保活会怎样

主界面的「常驻通知（前台服务）」开关可以关闭保活。

关闭后实测：

- 无障碍跳过功能**仍然可用**；
- 只要无障碍服务还开着，进程优先级**不变**（adj 仍是 100），存活能力基本不受影响；
- 但如果无障碍被系统或用户关闭，进程会掉到 adj=700 的普通后台待遇，容易被回收。

也就是说：**开着无障碍时，关不关前台服务对优先级没影响**。前台服务的价值在于「无障碍失效时的兜底」。

如果你对通知栏有强迫症，可以关掉，实际风险比想象中小。
